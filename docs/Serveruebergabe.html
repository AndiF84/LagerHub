Übergabe an die IT

LagerHub auf dem Windows Server

Was der Server braucht, damit die Lager-Aufgabenverwaltung dort im Firmennetz läuft. Die Anwendung selbst ist fertig und läuft bereits unter Windows — es geht ausschließlich um die Einrichtung.

Stand 7. September 2026 Betrieb rein intern, keine Erreichbarkeit aus dem Internet Ansprechpartner Andreas Funke

Worum es geht

LagerHub verteilt Arbeitsaufträge an das Lagerteam: Das Büro legt Aufgaben mit einzelnen Arbeitsschritten an, die Mitarbeiter holen sich die Schritte am Handy und melden sie fertig. Alle Beteiligten sehen Änderungen sofort, ohne die Seite neu zu laden.

Technisch sind es drei Teile: ein Node.js-Dienst mit der Programmlogik, ein Web-Dashboard für Büro und Leitung, und eine Handy-App für das Lager. Dashboard und Handy-App sind reine Dateien — HTML, JavaScript, Bilder —, die ein Webserver ausliefert. Nur der Node-Dienst läuft dauerhaft.

Kurz gesagt

Ein Windows-Dienst, eine IIS-Website mit zwei Adressen, ein Zertifikat, eine Datenbank. Kein Docker, kein Linux, keine Freigabe aus dem Internet.

Bitte bei der WLAN-Planung berücksichtigen

Benachrichtigungen gehen nicht direkt vom Server aufs Handy. Der Server schickt sie an den Push-Dienst des Handy-Herstellers, und das Handy holt sie von dort über seine eigene Verbindung ab. Beide Seiten brauchen also Internet. Ist das Hallen-WLAN vollständig abgeschottet und haben die Geräte keine SIM-Karte, kommt keine Benachrichtigung an — die App selbst funktioniert dann weiterhin vollständig, aber eben nur, solange sie offen ist.

Schritt 3

Adressen und Zertifikat

Der Teil, der zuerst stehen muss

Wir brauchen zwei Namen aus einer Domain, die der Firma gehört — zum Beispiel lagerhub.firma.de und app.firma.de. Beide zeigen im internen DNS auf die private IP des Servers. Nach außen wird nichts veröffentlicht.

Das Zertifikat holt win-acme über die DNS-01-Prüfung: Der Nachweis läuft über einen DNS-Eintrag statt über einen offenen Port, es genügt also eine ausgehende Verbindung. Ein Zertifikat für beide Namen reicht.

Warum dieser Umweg

Ein selbst ausgestelltes Zertifikat würde hier nicht genügen: Handys verweigern bei einem nicht vertrauenswürdigen Zertifikat die Installation als App und die Benachrichtigungen. Ein Zertifikat aus einer internen Zertifizierungsstelle müsste auf jedem einzelnen Handy von Hand eingerichtet werden — und bei jedem neuen Gerät erneut. Der Weg über einen echten Namen erspart das vollständig: Jedes Handy vertraut ihm sofort.

Schritt 4

IIS einrichten

Zwei Websites, dieselbe Struktur

Beide Websites sind gleich aufgebaut. Sie unterscheiden sich nur im Hostnamen und im Ordner mit den Dateien:

WebsiteDateien liegen inWeiterleitung
Dashboardlagerhub.firma.de …\LagerHub\frontend\dist /api und /ws → http://localhost:3000 Alles andere kommt aus dem Dateiordner. Anfragen auf einen unbekannten Pfad müssen auf index.html zeigen, sonst führt ein Neuladen innerhalb der App zu einem 404.
Handy-Appapp.firma.de …\LagerHub\pwa\dist

Die Regeln sind schon fertig

In beiden Ordnern liegt nach dem Bauen eine web.config. Sie bringt die Weiterleitung, den Fallback auf index.html, die fehlenden Dateitypen und die Zwischenspeicher-Regeln bereits mit — es muss also nichts von Hand in IIS eingetragen werden. Sie wird beim Bauen automatisch mitgeliefert und kann nicht vergessen werden.

Zwei Dinge stehen trotzdem nicht darin, weil sie am Server hängen und nicht an der Website: das Windows-Feature WebSocket Protocol und der eingeschaltete Proxy in ARR (IIS-Manager → Server → Application Request Routing Cache → Server Proxy Settings → Enable proxy). Ohne den zweiten Punkt antwortet /api mit 404.

Bitte einmal prüfen: kommt die echte Client-Adresse an?

LagerHub bremst Anmeldeversuche pro Adresse aus (zehn pro Minute) — die PIN ist vierstellig, ohne diese Bremse wäre sie zu raten. Dafür muss der Dienst die Adresse des Geräts sehen, nicht die des Servers. IIS reicht sie im Feld X-Forwarded-For weiter.

Kommt sie nicht an, sieht der Dienst jede Anfrage als 127.0.0.1 — dann teilen sich alle Mitarbeiter einen gemeinsamen Zähler und ab der zehnten Anmeldung im Haus wird jede weitere abgewiesen. Ein Blick ins Protokoll nach den ersten Anmeldungen beantwortet das sofort.

Das würde ich als Allererstes prüfen

Die Weiterleitung von /ws ist eine WebSocket-Verbindung, keine gewöhnliche Anfrage. Dafür muss das Windows-Feature WebSocket Protocol installiert und die Zwischenspeicherung in ARR für diesen Pfad abgeschaltet sein.

Daran hängt die gesamte Live-Aktualisierung: Ohne sie sehen Dashboard und Handy-App Änderungen erst beim Neuladen der Seite. Die Anwendung wirkt dann nicht kaputt, nur merkwürdig träge — deshalb fällt es erfahrungsgemäß erst im Betrieb auf. Ein kurzer Test direkt nach dem Einrichten spart hier viel Sucherei.

Schritt 5

Bauen und starten

Einmal einrichten, danach bei jeder neuen Version wiederholen

# Dienst: Abhängigkeiten, Datenbankstruktur, Programm bauen
cd backend
npm ci
npx prisma generate
npx prisma migrate deploy      # legt die Tabellen an bzw. aktualisiert sie
npm run build

# Dashboard und Handy-App bauen (Ergebnis landet je in dist\)
cd ..\frontend && npm ci && npm run build
cd ..\pwa      && npm ci && npm run build

# Dienst starten - im Betrieb übernimmt das der Windows-Dienst
cd ..\backend
npm start                      # hört auf Port 3000

Der Dienst wird mit NSSM auf node dist\index.js im Ordner backend eingerichtet, mit automatischem Start und Neustart nach einem Absturz. Ob er läuft, beantwortet http://localhost:3000/health — die Antwort lautet {"ok":true} und eignet sich direkt für eure Überwachung.

Die drei Dinge, die erfahrungsgemäß schiefgehen

Alle drei sind leicht zu vermeiden und schwer zu finden, wenn man sie übersieht.

1 — Zeitzone

Der Server muss auf Europe/Berlin stehen. LagerHub rechnet an mehreren Stellen mit der lokalen Uhrzeit: Feierabend, Mittagspause, die Erinnerung zum Arbeitsbeginn und die Tagesgrenze der Auswertungen. Läuft der Server auf UTC, unterbricht der Feierabend im Sommer zwei Stunden zu spät und die Tagesberichte schneiden an der falschen Stelle.

2 — WebSocket durch IIS

Siehe Schritt 4. Ohne das Windows-Feature WebSocket Protocol bleibt die Live-Aktualisierung stumm, ohne dass eine Fehlermeldung erscheint.

Eine Nebenwirkung ist inzwischen abgefangen: Die Verbindung ist die meiste Zeit still, weil Meldungen nur kommen, wenn wirklich etwas passiert. Ein Proxy trennt eine stille Verbindung nach einer Weile. LagerHub schickt deshalb alle zwanzig Sekunden ein Lebenszeichen und lädt nach einem Abriss den Stand neu nach — vorher hätte die Anzeige stillschweigend veralten können. Das ersetzt das Windows-Feature aber nicht.

3 — Datensicherung

Die Datenbank enthält die gesamte Auftrags- und Arbeitszeit-Historie. Für PostgreSQL ist pg_dump als geplante Aufgabe der übliche Weg. Bitte mit einplanen — eine Sicherung, die nie zurückgespielt wurde, ist keine.
