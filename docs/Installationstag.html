Die Etappen

der Reihe nach — jede baut auf der vorigen auf

Jede Etappe endet mit einer Prüfung. Erst wenn die stimmt, geht es weiter: Ein Fehler in Etappe 2 zeigt sich sonst erst in Etappe 8, und dann sucht man an der falschen Stelle.

01

Zeitzone prüfen

Vor allem anderen, weil es später niemand mehr nachvollzieht

IT2 min
tzutil /g

Muss W. Europe Standard Time ergeben. Falls nicht: tzutil /s "W. Europe Standard Time"

Warum zuerst: LagerHub rechnet an vielen Stellen mit der lokalen Uhrzeit — Feierabend, Mittagspause, Tagesgrenze der Auswertungen, Fälligkeit der Erinnerungen. Auf einem UTC-Server unterbricht der Feierabend im Sommer zwei Stunden zu spät und die Tagesberichte schneiden an der falschen Stelle. Das fällt erst nach Wochen auf.
Fertig, wenn tzutil /g die europäische Zeitzone meldet.
02

Grundsoftware installieren

Node, PostgreSQL, IIS mit seinen drei Erweiterungen

IT45 min
  • Node.js 22 oder neuer (LTS genügt)
  • PostgreSQL 16 oder neuer, offizieller Windows-Installer
  • IIS mit URL Rewrite, Application Request Routing und dem Windows-Feature WebSocket Protocol
  • NSSM (macht den Dienst) und win-acme (holt das Zertifikat)
node -v      // v22 oder hoeher
npm -v
psql --version
Das WebSocket-Feature wird am häufigsten vergessen. Ohne es läuft alles scheinbar — nur aktualisieren sich Dashboard und Handy-App nicht mehr von selbst. Es gibt keine Fehlermeldung, die App wirkt bloß träge. In Etappe 9 wird genau das geprüft.
Fertig, wenn Die drei Befehle Versionen ausgeben und im Server-Manager unter den IIS-Rollendiensten WebSocket Protocol als installiert steht.
03

Datenbank anlegen

Leere Datenbank plus eigener Benutzer — die Tabellen kommen später von allein

IT10 min
psql -U postgres
CREATE USER lagerhub WITH PASSWORD 'langes-passwort-nur-buchstaben-und-ziffern';
CREATE DATABASE lagerhub OWNER lagerhub;
\q
Das Passwort am besten ohne Sonderzeichen vergeben — lang, aber nur Buchstaben und Ziffern. Es wird gleich in Etappe 4 in eine URL eingesetzt, und dort beendet ein @ den Passwort-Teil: aus …lagerhub:pa@ss@localhost… wird ein Host namens ss. Die Verbindung läuft dann ins Leere, ohne dass die Zeile falsch aussieht. Betroffen sind @ : / ? # % &. Wer sie trotzdem will, muss den Wert kodieren — wie, steht in Etappe 4. Länge ersetzt Sonderzeichen hier vollwertig: 30 Stellen aus Buchstaben und Ziffern sind nicht zu raten.

Keine Tabellen von Hand anlegen — das erledigt Etappe 5. PostgreSQL hört nur auf localhost; von außen muss die Datenbank nicht erreichbar sein.

Fertig, wenn psql -U lagerhub -d lagerhub -c "select 1" durchläuft.
04

Einstellungen eintragen

Die Datei backend\.env — beim Stick-Paket sind nur noch zwei Werte offen

gemeinsam5 min
Kam das Projekt vom Übergabe-Stick, ist backend\.env schon ausgefüllt — auf Anweisung des Betreibers. Bereits eingetragen sind die Admin-PINs, die VAPID-Schlüssel für die Benachrichtigungen und der Crewmeister-Zugang; das JWT_SECRET wurde beim Packen frisch erzeugt. Offen sind nur noch zwei Werte, beide unten in der Tabelle markiert: DATABASE_URL/DIRECT_URL und CORS_ORIGIN. Diese Datei nicht mit .env.example überschreiben — dabei gingen genau die Werte verloren, die euch die Arbeit ersparen. Ein Hinweis dazu steht auch oben in der Datei selbst.

Nur bei einem Git-Klon ohne vorbereitete .env ist die Vorlage backend\.env.production.example die Grundlage, und diese beiden Werte müssen selbst erzeugt werden: 

// Anmelde-Schluessel (JWT_SECRET)
node -e "console.log(require('crypto').randomBytes(48).toString('base64'))"

// Schluesselpaar fuer die Benachrichtigungen (VAPID)
npx web-push generate-vapid-keys
EintragWert
DATABASE_URL
DIRECT_URL		 ← NOCH EINZUTRAGEN. Beide auf die lokale PostgreSQL aus Etappe 3. Format: postgresql://lagerhub:PASSWORT@localhost:5432/lagerhub. Enthält das Passwort Sonderzeichen, müssen sie kodiert werden — siehe Warnung unter der Tabelle
CORS_ORIGIN ← NOCH EINZUTRAGEN, sobald die Adressen feststehen: die beiden Hostnamen aus Etappe 6, mit Komma getrennt und mit https:// davor. Bleibt das Feld leer, läuft alles — der Dienst nimmt dann aber Anfragen von jeder Herkunft an und schreibt beim Start eine Warnung ins Protokoll
JWT_SECRET Beim Stick-Paket schon gesetzt (beim Packen erzeugt). Pflicht — ohne ihn startet der Dienst absichtlich nicht. Beim Ändern müssen sich alle neu anmelden
ADMIN_PINS Beim Stick-Paket schon gesetzt, vom Betreiber vorgegeben. Das ist der einzige Zugang in ein frisches System — die Datenbank ist leer, es gibt noch keinen Mitarbeiter. Format 1234:Name, mehrere mit Komma. Wird beim Start einmal gelesen: Änderungen wirken erst nach einem Neustart des Dienstes
VAPID_PUBLIC_KEY

NODE_ENV, TZ

Sonderzeichen im Datenbank-Passwort zerlegen die Verbindungszeichenfolge. Sie ist eine URL — ein @ im Passwort beendet dort den Passwort-Teil. Aus …lagerhub:pa@ss@localhost… wird ein Host namens ss, und die Verbindung läuft ins Leere, ohne dass die Zeile falsch aussieht. Betroffen sind @ : / ? # % &. Entweder ein Passwort ohne diese Zeichen vergeben — oder den Wert kodieren mit node -e "console.log(encodeURIComponent(process.argv[1]))" DAS_PASSWORT und die Ausgabe in die URL setzen (@ wird zu %40 und so fort). npm run db:check erkennt diesen Fall und sagt es.
Fertig, wenn npm run db:check im Ordner backend meldet Die Datenbank-Verbindung steht. In der .env steht dann kein [PASSWORT] mehr.
05

Tabellen anlegen

Beim Stick-Paket zwei Befehle — gebaut ist schon alles

IT5 min
Zuerst klären, welcher Weg gilt — daran hängt alles Weitere. Kam das Projekt vom Übergabe-Stick, ist es fertig gebaut und backend\node_modules liegt schon da. Dann weder npm ci noch npm run build ausführen: npm ci löscht node_modules als Erstes und lädt alles neu aus dem Internet. Auf einem abgeschotteten Server bricht es dabei ab — und der mitgelieferte Baum ist weg. Danach startet weder der Dienst noch kommt eine Datenbankverbindung zustande. Weg B gilt nur für einen Git-Klon ohne node_modules, und der braucht Internetzugang.

Weg A — Paket vom Stick (der Normalfall)

cd C:\LagerHub\backend
npm run db:check          // prueft die Verbindung, benennt die Ursache
npm run migrate:deploy    // legt die Tabellen an

Mehr nicht. frontend\dist und pwa\dist liegen fertig gebaut im Paket, ebenso der erzeugte Prisma-Client.

Weg B — Git-Klon ohne node_modules (nur mit Internetzugang)

// Dienst
cd C:\LagerHub\backend
npm ci
npm run db:generate
npm run db:check
npm run migrate:deploy
npm run build

// Dashboard
cd ..\frontend
npm ci
npm run build

// Handy-App
cd ..\pwa
npm ci
npm run build
Meldungen über neue Versionen ignorieren. Prisma weist bei jedem Aufruf auf eine neuere Version hin. Dieser Hinweis ist kein Arbeitsauftrag — am Installationstag wird nichts aktualisiert. Die Versionen im Paket sind aufeinander abgestimmt und geprüft; ein npm install oder npm audit fix holt im besten Fall nichts (kein Netz), im schlechteren eine Vorabversion. Aktualisiert wird beim Entwickler, nie hier.
Immer migrate deploy, nie migrate dev. Die Entwickler-Variante darf das Schema umbauen und im Zweifel die Datenbank leeren — auf einem Server mit echten Daten wäre das ein Totalverlust. deploy wendet ausschließlich die vorhandenen Migrationen an.
Fertig, wenn npm run migrate:deploy lief durch und meldet beim zweiten Aufruf No pending migrations to apply. In frontend\dist und pwa\dist liegen Dateien — beim Stick-Paket von Anfang an.
06

Dienst einrichten

Erst von Hand starten, dann als Windows-Dienst festzurren

IT20 min

Zuerst der Handstart, damit Startfehler direkt im Fenster sichtbar sind:

cd C:\LagerHub\backend
npm start                       // hoert auf Port 3000

// im zweiten Fenster
curl http://localhost:3000/health

Antwortet er mit {"ok":true}, wird er mit NSSM auf node dist\index.js im Ordner backend als Dienst eingerichtet — mit automatischem Start und Neustart nach einem Absturz. Danach das Handfenster schließen und den Dienst starten.

Fertig, wenn Der Server wurde einmal neu gestartet und /health antwortet ohne dass jemand etwas von Hand startet.

08

Zertifikat und Freigaben

Ohne gültiges Zertifikat keine App-Installation und keine Benachrichtigungen

IT30 min

win-acme holt ein Zertifikat für beide Namen über die DNS-01-Prüfung, trägt es in die IIS-Bindungen ein und legt die Erneuerung als geplante Aufgabe an. Dazu die ausgehenden Freigaben:

  • api.crewmeister.com — Anwesenheit aus der Zeiterfassung
  • Push-Dienste der Browser-Hersteller — Benachrichtigungen aufs Handy
  • Let's Encrypt und der DNS-Anbieter — Zertifikatserneuerung
  • Eingehend: 443 aus dem Firmennetz. Aus dem Internet nichts.
Fertig, wenn Beide Adressen sind von einem anderen Rechner im Netz über https erreichbar und der Browser zeigt kein Zertifikatswarnung.
09

Live-Verbindung prüfen

Der Test, der die häufigste Fehlkonfiguration sofort zeigt

gemeinsam5 min

Dashboard über die neue Adresse öffnen und anmelden. Oben links neben dem Logo steht der Verbindungsstatus:

  • ● Live — die Verbindung steht.
  • ● Verbinde… oder ● Getrennt, dauerhaft — die WebSocket-Weiterleitung greift nicht. Zurück zu Etappe 2 und 7: Windows-Feature installiert? ARR-Zwischenspeicher für /ws aus?
Fertig, wenn Der Kopf zeigt dauerhaft ● Live — und eine Änderung an einem Gerät erscheint am zweiten, ohne dass jemand neu lädt.

Datensicherung einrichten

Der Punkt, der gern auf „machen wir nächste Woche" rutscht

IT30 min

In der Datenbank liegt die gesamte Auftrags- und Arbeitszeit-Historie. Üblicher Weg ist pg_dump als geplante Aufgabe. 

pg_dump -U lagerhub -d lagerhub -F c -f D:\Backup\lagerhub_%DATE%.dump
Fertig, wenn Eine Sicherung wurde einmal zurückgespielt — in eine Testdatenbank, nicht in die echte. Eine nie zurückgespielte Sicherung ist keine.

Später: eine neue Version einspielen

Update-Paket vom Stick – Daten und Einstellungen bleiben

Der Normalfall: Update-Paket vom Stick

Der Entwickler liefert ein Update-Paket (LagerHub-Update-<Datum>.zip). Es ist für einen bereits eingerichteten Server gedacht und enthält bewusst keine .env: Datenbank-Kennwort, JWT_SECRET und PINs des Servers bleiben, wie sie sind. Internet braucht der Server dafür nicht. 

// 1. ZIP entpacken (vorher Rechtsklick - Eigenschaften - Zulassen)
// 2. update.bat per Rechtsklick "Als Administrator ausfuehren"
//    liegt LagerHub nicht unter C:\LagerHub, in einer Admin-PowerShell:
.\update.ps1 -Installation D:\LagerHub

Das Skript erledigt der Reihe nach:

  1. Datenbank sichern (pg_dump nach C:\LagerHub-Sicherungen) – scheitert das, bricht es ab, bevor irgendetwas geändert ist.
  2. Dienst anhalten – den Windows-Dienst findet es selbst (NSSM-Dienst mit Arbeitsordner backend); sonst -Dienst <Name> aus der Notiz von Etappe 6.
  3. Programmdateien austauschen – der alte Stand wird beiseitegelegt (die letzten drei bleiben). Eine angepasste web.config bleibt erhalten; die neue liegt dann als web.config.neu daneben.
  4. Datenbank prüfen und Schema nachziehen (db:check, migrate deploy).
  5. Dienst starten und auf /health warten.
Schlägt ein Schritt fehl, kommt der alte Stand automatisch zurück und läuft wieder. Das Fenster nennt die Ursache, das Protokoll liegt in C:\LagerHub-Sicherungen. Wurde die Datenbank-Migration schon begonnen, steht dort zusätzlich der pg_restore-Befehl für die Sicherung – meist ist er nicht nötig, weil neue Spalten den alten Stand nicht stören.

Angemeldete Benutzer bleiben angemeldet; Dashboard und Handy-App laden die neue Fassung beim nächsten Öffnen.

Alternative mit Internet: aus dem Git-Stand bauen

// 1. Dienst anhalten, 2. neuen Stand holen
git pull

// 3. bauen - Datenbankstruktur inbegriffen
cd backend  && npm ci && npm run db:generate && npm run migrate:deploy && npm run build
cd ..\frontend && npm ci && npm run build
cd ..\pwa      && npm ci && npm run build

// 4. Dienst wieder starten, dann /health pruefen
Dieser Weg setzt Internetzugang auf dem Server voraus. npm ci löscht node_modules und lädt alles neu von registry.npmjs.org. Ist der Server abgeschottet, bricht der Befehl ab und hinterlässt kein node_modules — der Dienst startet dann nicht mehr. Dann das Update-Paket oben verwenden.

migrate deploy gehört zwingend dazu. Bringt eine Version neue Felder mit — wie zuletzt die Erinnerungen — fehlen ohne diesen Schritt die Tabellen, und der betroffene Bereich läuft in einen Fehler, während der Rest normal weiterläuft. Vor einem Update mit Schema-Änderung gehört eine frische Sicherung dazu.

Die drei Dokumente im Zusammenhang

IT-Abstimmung — was vorab zu klären ist. Serverübergabe — was der Server braucht und warum. Dieser Laufzettel — die Reihenfolge am Tag selbst. Die technische Dokumentation der Anwendung liegt im Projektordner unter CLAUDE.md, die Vorlage der Server-Einstellungen unter backend\.env.production.example (die .env.example daneben ist die der Entwicklungsumgebung).
